# Volatility-hodlod

Testing whether the levels generated by the "μ ± k·σ/√(dev)" Pine indicator
produce real reactions on GC (gold futures), then — if so — building a
strategy on top of them.

Codex and Claude Code: work cooperatively here. Goal #1 is simply to find out
whether price reacts at these levels (2026 in particular shows several huge
top/bottom-tick reactions on GC). Goal #2, only after #1 looks real, is to
turn this into a tradeable strategy.

## Layout

- `indicator/mu_k_sigma.pine` — the original Pine v6 source, verbatim.
- `volgen/levels.py` — Python port of the indicator's level-placement math
  (cash open, VIX/GVZ-implied daily sigma, Initial Balance + extension,
  sigma offset, upper/lower level formulas). This is what reproduces the
  indicator's lines outside of TradingView.
- `volgen/reactions.py` — touch detection (ported from the indicator's touch
  test) plus reaction/continuation measurement once a level is touched.
- `scripts/backtest_levels.py` — CLI that ties the two together: feed it 1m
  GC OHLCV + GVZ daily data, it generates the session levels and reports
  touch rates and reaction sizes at several horizons (5/15/30/60/120m by
  default).
- `scripts/fetch_gvz.py` — refreshes `data/gvz_daily.csv`.
- `scripts/selftest.py` — smoke test against synthetic data (no large files
  needed); run this first to confirm the environment is sane.
- `data/gvz_daily.csv` — CBOE Gold ETF Volatility Index (GVZ) daily OHLC,
  2023-01-03 → present. **Source note:** FRED (series `GVZCLS`, the symbol
  the indicator actually requests as `CBOE:GVZ`) is unreachable from this
  sandbox's network egress (connection reset at the proxy). Yahoo Finance's
  `^GVZ` tracks the same CBOE index and provides full daily OHLC (FRED only
  publishes the close), so that's the source `fetch_gvz.py` uses. If you can
  reach FRED directly, pulling `GVZCLS` and diffing against this file would
  be a good sanity check — the two should match almost exactly on close.
- `data/gc_1m/` — **empty / gitignored.** This is where the user's 1-minute
  GC OHLCV (2023–2026) goes locally. It's too large for the repo, so it's
  never committed — drop the CSV here when working locally and point
  `--ohlcv` at it.

## Running the test

```
pip install pandas numpy
python3 scripts/selftest.py                      # sanity check, synthetic data
python3 scripts/backtest_levels.py \
    --ohlcv data/gc_1m/<your_gc_1m_file>.csv \
    --gvz data/gvz_daily.csv \
    --out-levels out/gc_levels.csv \
    --out-results out/gc_level_reactions.csv
```

The OHLCV CSV just needs a timestamp-like column (`timestamp`/`datetime`/
`date`/`time`) and `open`/`high`/`low`/`close` (case-insensitive). Naive
timestamps are assumed to be exchange-local (`America/New_York`); pass
`--tz` if yours are in UTC or another zone.

## Indicator parameters used for GC

From the Pine script's auto-detect table (`isGC` branch):

| param          | value      |
|----------------|------------|
| vol symbol     | `CBOE:GVZ` |
| sigma mult     | 1.15       |
| offset % sigma | 0.02       |
| IB length      | 30 minutes |

`sigmaDay = cashOpen × (priorGVZclose / 100) / √252`, and the level formulas
are `upper = (ibExtUp + impUp)/2 − sigmaOffset`,
`lower = (ibExtDn + impDn)/2 + sigmaOffset` — see `volgen/levels.py` for the
exact port (it mirrors the Pine line-by-line, including the no-lookahead
`close[1]` reference for the vol index).

## Open questions for the next pass

- Confirm the timestamp format/timezone of the 1m GC file before running —
  the level math is anchored to the 09:30 America/New_York RTH open, so a
  timezone mismatch will silently produce wrong levels.
- `reaction_threshold` in `backtest_levels.py` currently counts *any* move
  back through a touched level as a "reaction" — once we have real output,
  tune this (e.g. require N points of reversal) to separate "noise wobble"
  from genuine rejection.
- `evaluate_levels` only looks at the *first* touch of each level. Worth
  also tracking what happens on subsequent touches/retests once that's
  validated.
